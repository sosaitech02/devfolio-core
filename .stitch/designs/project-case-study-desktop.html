01 // CONTEXTO & PROBLEMA

El dilema de la gestión de contenido en ingeniería de software

El desarrollo de portafolios de ingeniería y plataformas técnicas frecuentemente cae en dos extremos ineficientes: el acoplamiento directo de casos de estudio dentro del código JSX/TSX de presentación, o la dependencia prematura de gestores de contenido externos (Headless CMS SaaS) como Sanity, Strapi o Contentful.

En el primer caso, editar un caso de estudio o mantener la paridad idiomática entre español e inglés requiere modificar componentes del árbol de React, generando commits de presentación ruidosos y aumentando drásticamente la fricción al documentar proyectos. En el segundo escenario, un CMS externo introduce llamadas asíncronas innecesarias en tiempo de ejecución, tokens de autenticación de terceros, riesgo de latencia y posibles rupturas de contrato tipado que TypeScript no puede garantizar de forma nativa durante el ciclo de compilación.

Para un ingeniero de software que busca máxima velocidad de renderizado, trazabilidad basada en Git y cero costos operativos, se requería una solución arquitectónica desacoplada: contenido puramente declarativo en Markdown enriquecido (MDX), con contratos de esquema estrictos y compilación en el servidor sin añadir un solo byte al paquete JavaScript del cliente.

02 // OBJETIVOS TÉCNICOS

Restricciones de diseño e invariantes requeridos

terminal
Validación estricta de tipos en compilación: Cero tolerancia a campos ausentes o tipos incorrectos en frontmatter mediante esquemas de validación Zod ejecutados antes del empaquetado final.
sync_alt
Paridad idiomática garantizada (ES / EN): El pipeline de CI rechaza cualquier pull request o despliegue si existe un proyecto en /content/projects/es que carezca de su traducción exacta en /content/projects/en.
database_off
Cero infraestructura externa o bases de datos: Almacenamiento exclusivo en el repositorio Git. El historial de versiones del software es simultáneamente el historial de cambios del contenido técnico.
bolt
0KB de sobrecarga JavaScript en el cliente: Aprovechamiento integral de React Server Components (RSC) para procesar AST y renderizar HTML semántico puro sin hidratación de contenido estático en el navegador.
03 // SOLUCIÓN & ARQUITECTURA

El pipeline desacoplado capa por capa

La arquitectura descompone el ciclo de vida del contenido en cuatro capas funcionales independientes. Cada capa opera con contratos unívocos y archivos fuente aislados, evitando dependencias circulares y permitiendo sustituir el motor de renderizado sin alterar los esquemas de datos:

Capa Responsabilidad Implementación Archivo Fuente
Contrato Tipado Validación de esquemas e inferencia estricta de tipos TypeScript Zod 3.x schema validator src/lib/content-schemas.ts
Capa de Lectura Extracción de metadatos frontmatter y separación de cuerpo Markdown gray-matter + Node fs/promises src/lib/projects.ts
Pipeline Render Compilación de AST, parseo de sintaxis de código y componentes MDX @mdx-js/mdx + remark-gfm src/lib/mdx.ts

04 // DECISIONES TÉCNICAS

Análisis comparativo de motores MDX

difference // DECISIÓN: @mdx-js/mdx con React 19 RSC vs Next-MDX-Remote vs Contentlayer

Durante la fase de diseño de devfolio-core, se evaluaron tres alternativas predominantes en el ecosistema React:

  • × Contentlayer: A pesar de su excelente experiencia de desarrollo en versiones previas de Next.js, el proyecto carece de soporte oficial activo, presenta problemas de compatibilidad con React 19 y Node 22+, y requiere hooks de empaquetado invasivos.
  • × next-mdx-remote: Si bien desacopla el contenido, añade serialización innecesaria entre servidor y cliente, forzando la inyección de componentes de hidratación en el frontend que incrementan el TTI (Time to Interactive).
  • ✓ @mdx-js/mdx nativo sobre React Server Components: Se seleccionó la compilación directa en tiempo de compilación. El servidor ejecuta el compilador MDX y genera un árbol de elementos de React puros que viajan al cliente como HTML inerte, reduciendo la huella de JavaScript de la página a prácticamente 0 KB.
05 // RETOS & SOLUCIONES

Ingeniería de robustez en producción

1 Verificación automatizada de paridad bilingüe ES / EN

Uno de los mayores riesgos en sitios con internacionalización manual es la divergencia de contenido: publicar un proyecto en español sin su correlativo en inglés. Para resolverlo, se programó un script en TypeScript (scripts/validate-content.ts) ejecutado como hook pre-commit mediante Husky y en el workflow de GitHub Actions. Si las listas ordenadas de slugs entre idiomas no coinciden al 100%, el proceso aborta con código de salida 1 e indica el archivo faltante.

2 Generación estática determinista sin cookies() dinámicas

Cualquier invocación accidental a headers() o detección dinámica de idioma en el layout raíz desactiva el renderizado SSG de Next.js, degradando las rutas a SSR dinámico. La solución radicó en mover la resolución de idioma a parámetros de ruta tipados (/[lang]/projects/[slug]), permitiendo a generateStaticParams() pre-calcular todas las combinaciones en build time.

3 Inyección de metadatos SEO tipados y esquemas JSON-LD

Se construyó una función de orden superior generateMetadata() que consume directamente el objeto tipado por Zod. Esto genera dinámicamente etiquetas OpenGraph bilingües, URLs canónicas con tags hreflang y metadatos de esquema estructurado schema.org sin duplicar cadenas de texto.
